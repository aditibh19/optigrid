# ML Forecasting Layer

Five forecasters, one shared training/evaluation utility. Every metric
below was actually computed by running `python ml/demo_forecasting.py` in
this repository (spec §10: "Do not fabricate metrics") — re-run it
yourself any time to reproduce or refresh these numbers.

## Models compared per forecaster

Each forecaster trains **Random Forest**, **Gradient Boosting**, and
**XGBoost** on an identical train/test split and reports held-out MAE,
RMSE, and R² for all three (`ml/model_utils.py`). The best (lowest RMSE) is
persisted to `ml/artifacts/*.joblib` for reuse without retraining on every
request.

**XGBoost availability:** if `xgboost` isn't installed in the environment,
`HistGradientBoostingRegressor` (scikit-learn's own histogram-based
gradient boosting, algorithmically similar to XGBoost) stands in for it —
labeled explicitly as a substitute in every printed result and returned
metric, never silently passed off as XGBoost itself.

| Forecaster | Best model | MAE | RMSE | R² |

## All data is SYNTHETIC — read this before citing these numbers

Every dataset here is generated by `ml/data_synthesis.py`, not sourced from
real electricity markets, grids, or charging stations (spec §10/§29). Each
generator injects a plausible daily/weekly seasonal pattern (price and grid
load double-peak in the morning and evening; solar follows a daylight bell
curve; station demand peaks at commute times) plus Gaussian noise, so the
metrics above measure "can these models recover a known, partially-noisy
seasonal pattern" — not "how well would this work on a real grid." That's
the right question for now: it validates the *pipeline* (feature
engineering, train/test discipline, model comparison, persistence) ahead of
plugging in real `electricity_prices` / `grid_load` / `solar_generation` /
`station_demand` rows once they exist (Phase 10+).

## A real finding: a bad score can mean the DATA generator is wrong, not the model

The charger queue predictor's first version scored **R² ≈ 0** (occasionally
slightly negative) — not because gradient boosting is bad at this task, but
because the synthetic generator's default station capacity (4) was rarely
exceeded by demand, so `queue_length` was almost always 0. A model that
always predicts "0" already gets a very low MAE on a near-constant target,
which is exactly what an R² near zero is telling you: the model isn't
beating a trivial baseline, because there's barely any real
signal-bearing variance to beat. Lowering the default capacity to 3 (and
raising peak-demand multipliers slightly) made contention a regular
occurrence, and R² jumped to 0.77. Worth stating directly in a viva: a
disappointing metric is a prompt to inspect the data before touching the
model.

## Train/test split for time series

Ordinary random splitting would leak information: a lag feature computed
from a chronologically later row could end up "predicting" an earlier one
during evaluation. `ml/model_utils.py::time_based_split` instead holds out
a *contiguous trailing block* (last 20% of the timeline) as the test set —
the model is always evaluated on data strictly after everything it trained
on, which is the only fair test for a forecaster that will run on live,
forward-moving time in production.

## Where each forecaster's output is used

| Forecaster | Consumer |
|---|---|
| Price | `optimization/reward_model.py` (via live/predicted price values passed into `step_cost`), Charging Timeline UI |
